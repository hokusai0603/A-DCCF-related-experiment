## 2. 主成本：UPF → NWDAF 的 EES 通知

- 請求 header 265 B（`POST /collector/upf-notify`，含 `X-Ees-*`）＋ JSON body；
- body = 外框 49 B（`{"notificationItems":[…],"correlationId":"corr-N"}`）＋ 每個 UE 一筆 item；
- 逐 SUPI 訂閱下每則通知固定 1 筆 item；
- NWDAF 回 `HTTP/1.1 204 No Content`（64 B）。

## 3. 擬合出的成本模型

每個 producer（UPF）在每個回報週期內，同時送出 k 則通知、每則 N 筆 item 時：

```
bytes = k·(a0 + b·N) + max(0, k−2)·c_conn + [P ≥ 30 s]·min(k, 2)·c_ka
```

| 參數 | 值 | 意義 | 來源 |
|---|---|---|---|
| **a0** | **556.7 B** | 一則通知在 keep-alive 連線上的固定開銷：請求 header、JSON 外框、204 回應、TCP/IP header 與 ACK | 實測：P < 30 s 的 9 格，「每則線上 bytes − b」對「新連線/則」迴歸的截距，R² = 0.99992 |
| **b**（JSON） | **469–479 B／item** | 一筆 item 的 JSON 長度。隨週期略增（1 s：469.5；5 s：474.6；10 s：475.1；30 s：478.6），因為用量和 throughput 數字的位數變多；全部範圍 464–480 | 實測 body |
| **b**（線上） | **488.9 B／item** | 多筆 item 時每多一筆的線上 bytes；比 JSON 多約 3.8%，是 TCP 分段（每 1,448 B 一個 52 B header）加上 ACK 的開銷 | 合成驗證（第 4 節） |
| **c_conn** | **359.3 B／新連線** | 新開一條 TCP 連線的額外開銷（SYN、SYN-ACK、ACK、FIN 交換） | 同 a0 的迴歸斜率 |
| **c_ka** | **102.5 B／閒置連線／30 s** | TCP keep-alive 探測與回應（2 × 52 B）。只在週期 ≥ 30 s 時出現 | 30 s 的 3 格：95.7–106.2 |

**這個模型對 12 格實測的預測誤差都在 ±0.18% 以內。**

### 為什麼有 c_conn：連線重用的上限

UPF 的 notifier 用 Go `http.Transport` 的預設值，**每個目的地最多保留 2 條閒置連線**（`MaxIdleConnsPerHost = 2`）。同一個 UPF 上 k 個訂閱在同一時間觸發時，有 k − 2 則必須新開 TCP 連線，送完後又被關掉。

實測「新連線/則」和 Σ max(0, k − 2) / 總通知數 完全一致：

| 訂閱 UE | 預測 | 實測 |
|---|---|---|
| 6 | 0.3333 | 0.3333 |
| 26 | 0.8462 | 0.840–0.846 |
| 46 | 0.9130 | 0.912–0.913 |

所以每則通知的實際固定成本會隨「同一 producer 同時觸發的訂閱數」增加：

| 同時觸發數 | 每則固定成本 |
|---|---|
| k ≤ 2 | 557 B |
| k = 23 | 約 885 B |

這是 producer 實作的特性，不是協定本身的成本。

### 為什麼有 c_ka：30 秒週期的 keep-alive

Go 的 dialer 與 server 端 TCP keep-alive 都是 30 秒：

- **週期 < 30 s：** 連線不會閒置那麼久，所以 1／5／10 秒的 9 格中 keep-alive 封包數為 0。
- **週期 = 30 s：** 每條閒置連線每個週期多一組探測與回應。p30-u6 的 capture 中有 184 個 keep-alive 封包，每個 52 B。

## 4. 合成驗證（使用者決定的方法 1）

在 5GC 開一個臨時接收端（`192.168.107.5:18080`，不是 NWDAF），回覆內容和 NWDAF 一模一樣（204、64 B）。

- **發送端：** 在 UPF-EES 上執行。
- **請求內容：**
  - header：真實 notifier 的 265 B 原樣重送，只改 `Content-Length`。
  - body：用 p1-u46 capture 中真實的 item 組成 N 筆，N = 1、2、3、4、6、8、12、16、23、32、46，每個 N 送 30 次，全部在同一條持續連線上。
- **限制：** 不寫進 NWDAF 或 MongoDB，也不改任何程式碼（`scripts/p1_synth*.py`、`p1_synth_run.sh`）。

| 擬合 | a | b | R² | 最大殘差 |
|---|---|---|---|---|
| JSON body | 47.9 B | 470.84 B／item | 0.9999993 | 17.9 B |
| 線上 IP bytes（請求＋ACK＋回應） | 550.2 B | 488.93 B／item | 0.999975 | 249 B（TCP 分段造成的階梯） |

- **線性成立。** 線上截距 550 B 和實測的 a0 = 557 B 相差 1.2%。
- **JSON 斜率** 470.8 B 和實測 item 長度（1 秒週期 469.5 B）一致。
- **量測注意事項：**
  - 5GC 網卡（e1000）的 GRO 會把多個 TCP 段合併後才交給 tcpdump，使 TCP 段數被低估。所以合成測試期間暫時用 `ethtool -K enp0s9 gro off` 關掉 GRO，測完立刻恢復成 `on`；這是 runtime 設定，不是設定檔。
  - GRO 開著時的結果另存為 `synth/gro_on_*`，作為對照。
  - 真實通知只有 783 B、一個 TCP 段，不受 GRO 影響。

## 5. H3：成本與 UE 數的關係

- **通知數完全線性：** 通知/秒 = 訂閱 UE 數 / 週期（4 個週期的 R² 都是 1）。
- **bytes/秒在這個矩陣內也近乎線性**（R² ≥ 0.9999995），但截距為負：1 秒週期時，斜率 1,385 B／UE，截距 −1,432 B/s。原因是每則通知的固定成本會隨同一個 UPF 上的訂閱數增加（第 3 節的 c_conn）。
- **嚴格來說：** bytes 對 UE 數是分段線性，取決於每個 producer 的訂閱數分布；本矩陣的 UPF 分布見第 1 節。

- **MongoDB：**
  - `nwdaf.upfTrafficData` 每則通知存一筆，筆數＝通知數。
  - 它是 time-series collection，壓縮後的大小在 10 分鐘內變化不穩定（db `dataSize` 差值甚至出現負值），所以用筆數表示，不換算成 bytes。
- **CPU：** 各 NF 的 CPU 大致與通知率成正比。最高的是 NWDAF 在 1 s／46 UE 時的 9.4%，負載很輕。

## 7. 給 P3 模擬器的成本模型（2026-11-11 使用者決定）

四項決定都依建議採用，已寫進 PREREGISTRATION 5.1、5.4（仍是草稿）；參數在 `sim_params.json`（`scripts/p1_params.py` 產生）。

**每則通知 bytes = a + Σ（每次回報）(r + n_stat × s)**，單位是線上 IP bytes、雙向合計。

| 參數 | 值 | 來源 |
|---|---|---|
| a | 556.7 B | 本文件的 a0 |
| r | 248.1 B | 實測 item 扣掉 10 個數值欄位後的部分：JSON 平均 237.9 B（233–239），乘以 1.0384 |
| s | 24.09 B | 10 個數值欄位的平均：JSON 23.2 B，乘以 1.0384 |
| 原始量測 | n_stat = 10，r + 10 × s = 488.93 B | 等於合成測試的 b_wire |

各項決定：

1. **樣本單位**：用兩層模型。每次回報付一次 r，每個統計量付一次 s。原本「每個統計量都算一筆 b」會讓 mean+max 的摘要比原始量測還貴，所以不採用。
2. **c_conn**：主分析不納入（a = 556.7 B）。敏感度分析用 a = 884.8 B（= a0 + c_conn × 21/23）。
3. **b 的單位**：用線上值。JSON 換算成線上 bytes 的比值是 b_wire / b_JSON = 488.93 / 470.84 = 1.0384。
4. **c_ka**：忽略。在 p = 30 s、46 UE 時，keep-alive 每秒約 13.7 B，只占 EES bytes 的 0.65%。

舉例（一個 UE、1 分鐘，主分析）：

| 策略 | bytes | 相對 B1 |
|---|---|---|
| B1 | 60 × 1,045.6 = 62,738 B | — |
| B2：p = 10 s、k = 1、mean+max | 5,118 B | −91.8% |
| B2：p = 1 s、k = 10、mean+max | 21,117 B | −66.3% |
| B2：p = 60 s、k = 1、mean+max | 853 B | −98.6% |

限制：b 會隨數值位數變化（本矩陣 464–480 B）。P2 的流量是 0.2–1 Mbps，比這裡的 5 pps ping 大，數字位數較多，預估每筆原始量測最多多出約 4%。模型參數固定，不另做修正。
